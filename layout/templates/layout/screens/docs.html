    Start here

    The layout app holds everything that is shared: every layout, partial and component, the styles, the scripts and the pictures. Other apps never copy any of it. Their pages pick a layout and fill in a few blocks with their own words.

    • Change a layout once and every page using it changes. A page only changes itself.
    • Each page shows only what it needs. It picks one layout, and the layout only carries the parts it uses.
    • A page writes its own content in plain HTML. Only the frame (header, menus, footer) comes from the layout. The fields of a form, the cards and the sections are written in the page itself, so you can read the page top to bottom and see exactly what it shows. The shared CSS classes give it the look.
    • The layout decides how a page looks, never who may see it. Access is checked in the view (Public, private, staff).

    See every part working on the layout gallery. This page and the gallery are open while DJANGO_DEBUG=True; otherwise only staff can open them.

    How a page is drawn

    1. A view checks who may open the page, then renders a template.
    2. The template starts with {% verbatim %}{% extends "layout/…" %}{% endverbatim %} and fills a few blocks.
    3. The layout adds its header, menus, sidebar and footer.
    4. layout/base.html, the one HTML skeleton, adds the <head>, styles, scripts, loader and toasts.
    {% verbatim %}view  →  your template  →  a layout (public, user, admin, pages/banner…)  →  layout/base.html{% endverbatim %}

    Every template also gets one variable, layout, from layout/context_processors.py. It holds the site name, the menus this person may see, the sign-in links, the toast and loader settings, and the person's own layout choices.

    A new page

    For example, a FAQ page in the website app (frontend):

    1. The view

    {% verbatim %}# frontend/views.py
from django.shortcuts import render
from django.urls import reverse
from layout.access import public

@public
def faq(request):
    return render(request, "frontend/faq.html", {
        "breadcrumbs": [("Home", reverse("frontend:home")), ("FAQ", None)],
    }){% endverbatim %}

    2. The address

    {% verbatim %}# frontend/urls.py
path("faq/", views.faq, name="faq"),{% endverbatim %}

    3. The template: pick a layout, fill its blocks

    {% verbatim %}{# frontend/templates/frontend/faq.html #}
{% extends "layout/pages/banner.html" %}
{% block title %}FAQ{% endblock %}
{% block heading %}Good to <em>know</em>{% endblock %}
{% block banner_text %}Answers to common questions.{% endblock %}
{% block content %}
  <div class="panel"><p>…</p></div>
{% endblock %}{% endverbatim %}

    4. The menu (optional)

    {% verbatim %}# config/settings.py → LAYOUT["PUBLIC_NAV"]
{"label": "FAQ", "url": "frontend:faq", "icon": "info"},{% endverbatim %}

    Write <em>…</em> in a heading for the italic crimson word. Breadcrumbs are optional: pass breadcrumbs from the view and the layout draws them.

    A new app

    A future app (accounts, shop, blog…) uses the same layouts. Nothing is copied.

    1. python manage.py startapp shop, then add "shop" to INSTALLED_APPS in config/settings.py.
    2. In config/urls.py, above the frontend line: path("shop/", include("shop.urls")).
    3. Choose who may open each page in its view (next section).
    4. Put templates in shop/templates/shop/. Each one starts with {% verbatim %}{% extends "layout/…" %}{% endverbatim %}.
    5. Add links to LAYOUT in settings: PUBLIC_NAV, USER_NAV, ADMIN_NAV or ACCOUNT["NAV"].
    {% verbatim %}# shop/views.py
from django.contrib.auth.decorators import permission_required
from django.shortcuts import render
from layout.access import public, private, staff_only

@public
def products(request):                       # → layout/pages/listing.html
    return render(request, "shop/products.html", {...})

@private
def orders(request):                         # → layout/user.html
    return render(request, "shop/orders.html", {...})

@staff_only
@permission_required("shop.change_product", raise_exception=True)
def stock(request):                          # → layout/admin.html
    return render(request, "shop/stock.html", {...}){% endverbatim %}
    {% verbatim %}{# shop/templates/shop/orders.html #}
{% extends "layout/user.html" %}
{% block title %}Your orders{% endblock %}
{% block heading %}Your orders{% endblock %}
{% block page_actions %}<a class="button button--small" href="…">New order</a>{% endblock %}
{% block content %}…{% endblock %}{% endverbatim %}

    An accounts app also tells the layouts where signing in happens, once, in settings:

    {% verbatim %}LOGIN_URL = "accounts:login"
LAYOUT["ACCOUNT"] = {
    "LOGIN_URL": "accounts:login", "SIGNUP_URL": "accounts:signup",
    "LOGOUT_URL": "accounts:logout", "PASSWORD_RESET_URL": "accounts:password_reset",
    "MODAL": True, "NAV": [{"label": "Your orders", "url": "shop:orders"}],
}{% endverbatim %}

    From then on, the header's Sign in, Create account and Sign out links and the account modal all use them.

    Public, private, staff

    Access is always decided in the view, with layout/access.py:

    Function viewsClass-based viewsWhoOthers get
    @public(nothing)Everyone-
    @privatePrivateMixinSigned-in peopleThe sign-in page
    @staff_onlyStaffMixinActive staffSign-in page, or 403 if signed in
    @dev_or_staff-Anyone while DEBUG, otherwise staff404
    • Add @permission_required("app.codename", raise_exception=True) under the decorator when a page needs a Django permission.
    • Safety net: user.html only shows its content to signed-in people, and admin.html only to active staff. Anyone else sees a notice instead, so a forgotten decorator still doesn't leak a private page.
    • Hiding a menu link is never the protection: give the link "perm" to hide it, and still check in the view.

    Blocks

    Every layout is built from the blocks of layout/base.html. A page fills them, empties them to hide a part, or adds to them with {% verbatim %}{{ block.super }}{% endverbatim %}.

    BlockWhat it is
    titleThe browser tab title (the site name is added after it)
    description, metaThe page description for search engines; extra meta tags
    styles, scriptsExtra CSS / JS files for one page (<link> / <script src>; never inline code)
    body_classExtra class on <body> for one page
    nav_modesolid (default), transparent (header over a picture until you scroll) or static
    loaderThe page loader; empty it to skip the loader on one page
    header, footerThe header and footer
    heroFull-width area under the header (pictures, bands)
    sidebarThe side menu (user and admin layouts)
    mainWraps everything in <main>; private layouts use it to hide content
    breadcrumbsThe breadcrumb trail (from the view's breadcrumbs)
    page_header, heading, page_actionsThe heading row: its title, and buttons beside it
    contentThe page's own content
    toastsWhere toasts appear
    modalsModal templates this layout needs (the public layout puts the account modal here)
     
    {% verbatim %}{% block breadcrumbs %}{% endblock %}            {# no breadcrumbs on this page #}
{% block page_header %}{% endblock %}            {# no heading row #}
{% block footer %}{% endblock %}                 {# no footer #}
{% block modals %}{% endblock %}                 {# no account modal #}
{% block nav_mode %}transparent{% endblock %}    {# header over a picture #}
{% block scripts %}<script src="{% static 'shop/js/cart.js' %}" defer></script>{% endblock %}{% endverbatim %}

    Error pages

    403.html, 404.html and 500.html are in layout/templates/ and use the centered layout. Django uses them automatically when DJANGO_DEBUG=False.

    User, admin, auth, plain

    • layout/user.html (private): the public header and footer, plus a sidebar with the person's name and LAYOUT["USER_NAV"]. Use with @private.
    • layout/admin.html (staff): the admin header, a dark sidebar with LAYOUT["ADMIN_NAV"] and a small footer. Use with @staff_only. The start page of the staff area is LAYOUT["ADMIN_HOME_URL"].
    • layout/auth.html: a picture with a quote beside the form, and no menus. Change them with the auth_image, auth_quote and auth_quote_by blocks.
    • layout/plain.html: only the page. It has no loader, breadcrumbs, header or footer.
    {% verbatim %}{% extends "layout/auth.html" %}
{% block title %}Sign in{% endblock %}
{% block heading %}Sign in{% endblock %}
{% block content %}
  <form class="form" method="post" novalidate>{% csrf_token %}
    …the username and password fields, written out (see Forms and fields)…
    <button type="submit" class="button button--block">Sign in</button>
  </form>
{% endblock %}{% endverbatim %}

    Forms and fields

    Write each field in the page. A full example is frontend/templates/frontend/contact.html. One field looks like this:

    {% verbatim %}<div class="field{% if form.email.errors %} is-invalid{% endif %}" data-field data-type="email">
  <label class="field__label" for="id_email">Email <span class="field__req">*</span></label>
  <div class="field__control">
    <span class="field__icon">{% include "layout/partials/icon.html" with name="mail" %}</span>
    <input type="email" id="id_email" name="email" required value="{{ form.email.value|default_if_none:'' }}">
    <span class="field__end">
      <button type="button" class="field__btn" data-field-clear aria-label="Clear email" hidden>{% include "layout/partials/icon.html" with name="x" %}</button>
    </span>
  </div>
  <p class="field__error">{{ form.email.errors.0 }}</p>
</div>{% endverbatim %}
    PartWhat it does
    class="field", data-fieldThe look, and turns on the ✕ button and the live checks (layout/js/fields.js)
    data-typetext, email, url, password, phone, textarea, checkbox, number: which check runs
    required, minlength, maxlengthNormal HTML rules on the input, checked while typing
    field__iconThe icon at the start (any icon name); leave it out for none
    data-field-clear … hiddenThe ✕ button; it shows itself once there is text
    data-field-eyeThe show/hide button for passwords (put it after the ✕)
    field__end-iconAn icon at the end
    data-match="id_password1"Must be the same as that field (repeat password)
    field__help, field__errorA hint; the error (the server's message, or the live one)
    is-invalidRed border when the server found a problem

    Put {% verbatim %}{% if form.errors %}{% endverbatim %}<div class="form-errors" role="alert">…</div>{% verbatim %}{% endif %}{% endverbatim %} at the top of the form for a summary. A password field gets both end buttons:

    {% verbatim %}<span class="field__end">
  <button type="button" class="field__btn" data-field-clear aria-label="Clear password" hidden>{% include "layout/partials/icon.html" with name="x" %}</button>
  <button type="button" class="field__btn" data-field-eye aria-label="Show password" aria-pressed="false">{% include "layout/partials/icon.html" with name="eye" %}</button>
</span>{% endverbatim %}
    • Errors: each field is checked while typing, with the server's own messages. A form with problems isn't sent; the first problem gets focus and a toast explains. The server still checks everything. Errors for the whole form show at the top, and each field's errors under it.
    • The Django form still checks everything on the server. Keep a form class in forms.py and give each input the same name as the form field.
    • Checkbox: <div class="field field--check" data-field data-type="checkbox"><label class="check"><input type="checkbox" name="agree" required><span>I agree</span></label>…
    • Radio buttons: a <fieldset class="field field--choices"> with a <div class="radio-row"> of labels (see layout/templates/layout/screens/preferences.html).

    Toasts

    Every Django message appears as a toast. Nothing else is needed:

    {% verbatim %}from django.contrib import messages
messages.success(request, "Saved.")          # also .info, .warning, .error
return redirect("shop:orders"){% endverbatim %}

    From a page: <button data-toast='{"message": "Copied", "type": "success"}'>. In JavaScript: Layout.toast("Copied", {type: "success", title: "Done", duration: 5000, position: "bottom-right"}). LAYOUT["TOASTS"] sets the position and time. Toasts always appear above an open modal.

    Loading

    • Page loader: covers the page until it is ready. Settings: LAYOUT["LOADER"] (PAGE, STYLE spinner/dots/pulse, TEXT). Empty {% verbatim %}{% block loader %}{% endverbatim %} to skip it on one page.
    • Between pages: a thin line at the top (NAVIGATE: bar, loader or none).
    • A form, link or button: data-loading='{"text": "Sending", "place": "center"}', where place is center, fullscreen, top-left, top-right, bottom-left or bottom-right.
    • The button that sent a form shows a spinner and can't be pressed twice.
    • JavaScript: var l = Layout.loading({text: "Saving"}); l.hide() and Layout.progress.start() / .done().

    Modals, confirm, tabs

    {% verbatim %}<a href="/terms/" data-modal='{"template": "#terms", "title": "Terms", "size": "lg"}'>Terms</a>
<template id="terms">
  <p>…</p>
  <button type="button" class="button" data-modal-close>OK</button>

    • size: sm, md, lg or full. place: "right" makes a side panel. tab opens on a tab inside the template.
    • Without JavaScript the link simply opens its page. A modal's content always comes from a <template> in the page.
    • Ask first: data-confirm='{"title": "Delete?", "message": "…", "confirm": "Delete", "danger": true}' on a link, button or form.
    • JavaScript: Layout.modal({...}), await Layout.confirm({...}) and await Layout.alert({...}).

    Account modal

    • "Sign in" in the header opens a modal (layout/partials/auth_modal.html). Only the public layout carries it, and only for people who aren't signed in.
    • The layout only draws it. The forms post to LAYOUT["ACCOUNT"] addresses, and the app behind them checks everything.
    • Sign in posts to LOGIN_URL. For now that's Django's admin sign-in, so only staff can sign in until an accounts app exists.
    • Register: the tab and the "Create account" button appear only once SIGNUP_URL exists.
    • PASSWORD_RESET_URL adds "Forgot your password?". "MODAL": False turns the modal off, so the links open the pages.
    • To use it on another layout, put it in that layout's modals block. To drop it on one page, empty {% verbatim %}{% block modals %}{% endblock %}{% endverbatim %}.

    Menus and sidebars

    All menus live in LAYOUT in config/settings.py. Each one is a list:

    {% verbatim %}"ADMIN_NAV": [
    {"label": "Dashboard", "url": "layout:staff_home", "icon": "home"},
    {"heading": "Manage"},                                               # a small heading
    {"label": "Orders", "url": "shop:orders", "icon": "file",
     "perm": "shop.view_order", "badge": "shop.badges.new_orders"},      # needs a permission; shows a number
    {"label": "Shop", "icon": "globe", "children": [                     # a group that opens
        {"label": "Products", "url": "shop:products", "icon": "file"},
    ]},
    {"label": "Reports", "url": "shop:reports", "staff": True, "groups": ["Managers"]},
],{% endverbatim %}
    • url is a URL name (or a path that starts with /). A link to a page that doesn't exist yet is simply left out.
    • perm, groups and staff hide the link from people who can't use it. Empty groups and lonely headings disappear.
    • badge names a function that takes the request and returns a number (0 hides it); see layout/badges.py.
    • The current page's link is marked automatically.
    • Sidebars fold to icons with their ⇤ button (remembered in the browser; the default comes from Layout preferences). On phones they become a panel that slides in.

    Everything the layouts read is in LAYOUT in config/settings.py. Values with fixed choices are checked, so a typo falls back to the default.

    KeyWhat
    SITE_NAME, DESCRIPTIONShown in the header, footer, titles and search results
    HOME_URL, ADMIN_HOME_URLWhere the logo goes; the staff area's start page
    ACCOUNTLOGIN_URL, SIGNUP_URL, LOGOUT_URL, PASSWORD_RESET_URL, MODAL, NAV
    PUBLIC_NAV, FOOTER_NAVThe header menu; the footer's second column
    USER_NAV, ADMIN_NAVThe sidebars of the user and admin layouts
    TOASTSPOSITION (top-left … bottom-right), DURATION (ms, 0 = stays)
    LOADERPAGE, STYLE, TEXT, NAVIGATE

    GROUP_DEFAULTSLayout choices for members of a group, e.g. {"Editors": {"sidebar": "collapsed"}}

    Look and themes

    • Colours, fonts and sizes are variables at the top of layout/static/layout/css/layout.css (--primary, --secondary, --font-display, --radius…). Change one and every page follows.
    • For each person: Layout preferences (theme light/dark, sidebar, spacing). Only fixed choices are accepted. For a whole group, use GROUP_DEFAULTS.
    • A new preference: add a field with choices in layout/models.py (plus DEFAULTS), add it to the form, run makemigrations and migrate, then use it in base.html as a data-… attribute with matching CSS.
    • Change a layout for everyone: edit its file in layout/templates/layout/, never a copy in another app.

    Every screen

    Every layout adjusts by itself. Nothing is needed in your pages, except wrapping wide tables in table-wrap.

    • Phones: the menu folds into a button, sidebars slide in, columns stack, and the page never scrolls sideways. Notched screens keep content clear of the notch.
    • Touch: bigger buttons and links. Hover effects only run on devices that can hover, and form text is at least 16px so phones don't zoom in.
    • Tablets get a tighter menu. Short screens (phones turned sideways) get smaller pictures.
    • Large screens and TVs: from 1920px wide the text steps up, so pages read well from a distance, and focus outlines get thicker for remote controls.
    • Reduced motion, high contrast and printing are handled too.

    Security checklist

    1. Every view uses @public, @private or @staff_only, plus @permission_required when it needs a permission.
    2. Never write inline scripts, inline styles or on… attributes: the security policy blocks them. Use files in static/ and the data-… attributes above.
    3. Every POST form has {% verbatim %}{% csrf_token %}{% endverbatim %}.
    4. Never use |safe or mark_safe on anything a visitor could have typed. Never build a class name, attribute or template path from user input: use fixed choices.
    5. Secrets stay in .env. Before going live: DJANGO_DEBUG=False, python manage.py check --deploy and python manage.py collectstatic.

    Problems and answers

    My page has no header or styles

    The template must start with {% verbatim %}{% extends "layout/…" %}{% endverbatim %}, and the view must use render(request, …) so the layout variable is there.

    A menu link doesn't show

    Its URL name doesn't exist (check app_name and name=), or the person lacks its perm, groups or staff.

    A private page shows "Please sign in" even though it should work

    The page uses user.html or admin.html and the visitor isn't allowed. That's the safety net working; check the view's decorator and the account.

    My button or script does nothing

    Inline scripts and on… attributes are blocked. Put the code in a static file and add it with the scripts block.

    The new page gives "Page not found"

    Check its line in the app's urls.py, and that the app is included in config/urls.py (new apps above the frontend line).

    I changed CSS or JS but see no difference

    Reload without the cache (Ctrl+F5). In production, run collectstatic again; file names then change with each version.
